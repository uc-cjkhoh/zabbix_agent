# D15 — Llama is reachable from the LAN only through an authenticated proxy

**Status:** owner decision (2026-11-23): the owner asked to reach the model remotely and chose "proxy with API key" and port 18081.

**Decision:** `zbxai_edge` (an unprivileged nginx) publishes `0.0.0.0:18081` and forwards to `zbxai_llama`. Every path except `/health`
needs the API key, as `Authorization: Bearer <key>` or as basic auth (user `llama`, password the key) so a browser can open the web UI.
`zbxai_llama` stays on the internal `zbxai_model` network only; the proxy is on `zbxai_front` and `zbxai_model`.

**Why not publish llama directly:** Docker cannot publish a port on an `internal: true` network, so llama would have to join a
non-internal network and lose its egress block ([D12](d12-operational-data-stays-in-network.md)). `llama-server` also has no
authentication of its own unless `--api-key` is set, and allows all origins.

**Consequences:**
- The key is generated by `scripts/edge-init.sh`, kept only in the git-ignored `deploy/secrets/llama-api-key` (mode 0600) on the testbed and in the
  config volume `zbxai_edge_conf`. It is never printed, logged or put in this KB. `edge-init.sh --rotate` replaces it; restart `zbxai_edge` after.
- Binding `0.0.0.0` means every interface of the testbed, including the LAN 10.168.48.0/22. Plain HTTP: the key travels in clear text on the LAN. Use a tunnel or add TLS before using it across an untrusted network.
- `zbxai_front` is not internal, so the proxy can reach out; it only forwards, and nothing at run time depends on that. Same honest gap as Grafana in
  the [topology](../architecture/topology.md) section 3.
- **D8 and D11 still hold.** The proxy is a development convenience for chatting with the model, not a notification channel, and the model has no path to
  Zabbix data (the MCP server and the worker are not built; model lookups stay off). Grafana remains the only notification surface.
- **CORS:** `llama-server` echoes any `Origin` but sends no `Access-Control-Allow-Credentials`, so a page on another site cannot read authenticated replies (checked 2026-11-23).
- **Not yet verified in a real browser:** the checks use `curl` only. They confirm the basic-auth challenge on 401, `/` returns HTML, and a streamed chat with basic
  auth returns `data:` events; the browser prompt and the UI itself have not been opened by us.
- Phase 1 later adds Grafana and Zabbix web to the same `zbxai_front` network; it already exists with the same name and subnet.

**Verified (2026-11-23):** from the workstation across the LAN: `/health` open (200); no key and a wrong key give 401; the key gives 200 on the API and the web UI;
a chat completion answers. llama's egress is still blocked after the change. firewalld did not block the published port (its rules are still unreadable here).
